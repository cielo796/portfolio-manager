## 旧表記から新キーへの対応

既存の `normalizeSectorKey()` で必要な旧表記を変換できるため、対応表への追加は不要だった。前後の空白を除き、小文字化し、空白・ハイフンをアンダースコアに置換して判定する。

| 旧表記・別名 | 新キー |
| --- | --- |
| `Technology` / `Tech` / `Information Technology` / `IT` | `technology` |
| `Communication` / `Communication Services` / `Telecom` | `communication` |
| `Consumer` / `Consumer Cyclical` / `Consumer Discretionary` | `consumer_discretionary` |
| `Consumer Defensive` / `Consumer Staples` | `consumer_staples` |
| `Healthcare` / `Health Care` | `healthcare` |
| `Finance` / `Financial` / `Financial Services` / `Financials` | `financials` |
| `Industrial` / `Industrials` | `industrials` |
| `Energy` | `energy` |
| `Materials` / `Basic Materials` | `materials` |
| `Utility` / `Utilities` | `utilities` |
| `Real Estate` / `Realestate` / `REIT` | `real_estate` |
| `ETF` | `etf` |
| 未知の文字列 / `Other` | `other` |
| 既存の正規キー13種類 | 同じキーを維持 |
| マイグレーション時の旧 `Cash` / `FX` | `null` |
| 現金・FXの行 | 入力された sector にかかわらず `null` |

既存の株式行で sector が null・空文字の場合、マイグレーションでは仕様どおり `normalizeSectorKey()` により `other` とする。新規保存・明示的な空欄更新・バックアップ取込で未指定の場合は `resolveSectorForSymbol()` で自動判定する。

### DB・API の確認

- 本物の DB・WAL・SHM をファイルとしてコピーし、SQLite で開く対象はコピーだけに限定した。
- コピーDBは起動前の `user_version = 0` から、`SQLITE_DB_PATH=<コピーDB> next start -p 3998` による起動と `/api/portfolio-data` の取得後に version 2 へ移行した。保有7行すべてが `SectorKey` または null で、sector 以外の全フィールドは移行前と一致した。
- 存在しない新規パスでも同じ方法で起動し、version 2、シード7行、6758の `consumer_discretionary` と FX の null を確認した。
- 各DBで POST を10ケース、PATCHを30ケース実行した。旧表記、未指定、null、空白、マスタ未収録銘柄、日本株、現金、FXを含み、`Technology` → `technology`、`CASH` + `Cash` → null の保存・応答を確認した。
- 各DBで旧表記の sector を含むバックアップを API 経由で取り込み、株式の正規化と現金・FXの null 保存を確認した。
- コピーDB・新規DBをそれぞれ再起動し、保有の全フィールドが再起動前と一致することを確認した。
- 両DBで `PRAGMA integrity_check = ok`、`foreign_key_check` が空であることを確認した。

### 追加の実装確認

- インメモリDBで33ケースの移行を確認した。旧表記、正規キー13種類、未知値、空文字、null、旧 Cash・FX、sector に誤値が入った現金・FXを対象とした。
- version 2 の UPDATE をトリガーで失敗させ、全行と user_version のロールバック、外部キー有効状態を確認。トリガー除去後の再実行も成功した。
- 適用済みの移行を再実行しても UPDATE が発生しないことと、version 2 単独適用時には外部キー切替が発生しないことを確認した。
- `getDb()` を3回呼び、WAL・外部キー有効化は初回だけで、2回目以降は追加の PRAGMA が発生しないことを確認した。
- 実際の `usePortfolio()` を副作用を抑えた状態で実行し、株式3分類・現金・FXへの集計、日本語ラベル、共通色を確認。現金行に誤った株式セクターを設定しても現金に分類された。
- 配分色は15キーすべてに設定され、重複する色がないことを確認した。

### 後片付け・元DBの保護

本物の `data/portfolio.db`・`-wal`・`-shm` の SHA-256 は検証前後で一致した。起動したサーバーはすべて停止し、3998番ポートに待ち受けが残っていないことを確認した。一時スクリプト・コピーDB・新規DB・WAL・SHMを削除し、検証用ディレクトリも削除した。

## 判断したこと

- 正規化は DB 層の作成・更新にも適用し、API 以外からの書き込みにも同じ規則を適用する。バックアップ・シードとは新設のヘルパーを共有する。
- `Holding` 型の変更は許可範囲外のため維持し、既存の optional 表現は内部で使う。永続化と API 応答では現金・FXを明示的な null に統一する。
- セクター選択の空欄は「セクターを自動判定」と表示する。PATCHで sector を省略したときは現在値を維持し、空文字・null の明示指定なら自動判定する。
- 既存13色を対応する新キーへ引き継ぎ、新たに必要な生活必需品とETFだけに色を追加した。表示名と集計キーを分離して、ラベルに依存した分類を避けた。
- 依存追加と禁止された Git 操作は行っていない。
