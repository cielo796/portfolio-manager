# T18 記録（売買・配当）実装レポート

実施日：2026-10-23

## 実装内容

`/records` に売買・配当の一覧、年・種別の絞り込み、CSV出力、年別の円集計、12か月の配当グラフ、追加・編集・削除を実装した。購入は手数料込みの移動平均、売却は数量減算と現地通貨の実現損益計算、配当は税引前金額の記録を行う。変更はSQLiteトランザクション内で再計算し、途中の超過売却を含む不正操作は全体をロールバックする。

保有画面の「決済」は、全数量を初期値とする「売却を記録」への導線に変更した。記録なしの保有削除は編集ダイアログ内に残し、2回押す方式にした。

実ユーザーの `data/portfolio.db` は開いていない。DBを伴うコマンドは `PM_FORBID_REAL_DB=1` と一時DBパスを設定して実行した。依存追加、コミット等のGit変更操作は実行していない。

### 本番HTTPで確認した値

専用シンボル `T18VERIFY` を既存シード口座に登録して検証した。

1. 購入：10株、単価100、手数料10 → 数量10、平均取得単価101。
2. 売却：4株、単価130、手数料2 → 数量6、平均取得単価101、実現損益114。
3. 配当：6株、1株あたり2 → 金額12 USD、保有数量6のまま。
4. 購入単価を110に編集 → 数量6、平均取得単価111、売却の実現損益74に再計算。
5. 7株の売却、および売却が残る状態で購入を削除 → いずれも400。数量6を維持。
6. 配当・売却を削除 → 数量10、平均取得単価111。購入も削除 → 保有一覧から消える。

### 全体テストの失敗

`src/lib/db/sync-schema.test.ts:77` の「バージョン2の既存データを保持して移行し、再実行しても変わらない」が失敗する。

このテストは現行スキーマから同期列だけを除去し、列数固定のINSERTで旧スキーマを再現する。最終コードでは、連動保有を守るトリガーを残したまま取引の `deleted_at` を削除しようとして、`error in trigger keep_ledger_holding after drop column: no such column: deleted_at` になる。トリガーを除いても、T18の開始残高2列・取引3列が残り、列数固定INSERTは失敗する（途中の実行で `table holdings has 14 columns but 12 values were supplied` を確認）。

`sync-schema.test.ts` はT18で変更を許可されたファイルに含まれないため変更していない。現行スキーマを加工する方式を、旧バージョンのDDLを明示する方式に変更する修正が必要。これはT18のスキーマ追加で顕在化した失敗であり、全体テスト成功とは扱っていない。

## 判断したこと

- **開始残高の永続化**：手入力済みの保有に最初の記録を反映する直前の数量・単価を、保有の `ledger_opening_shares` と `ledger_opening_cost` に保存する。取引の編集・削除やプロセス再起動後も開始残高から再計算するため、指示書の取引3列に加えてこの2列を設けた。
- **旧履歴との境界**：マイグレーションや単なる新規追加では旧取引を保有へ再加算しない。旧売買が残る銘柄で初めて編集・削除する場合は、指示書どおり同じ口座・銘柄・市場の全取引を連動し、開始残高ゼロから再構築する。以後は全履歴を再計算する。手入力残高より取引履歴が優先されるため、画面に注意を表示する。履歴の途中で数量が負になる場合は400で全変更を取り消す。
- **数量ゼロ**：既存の `holdings.shares > 0` 制約を維持し、全数売却は保有行を論理削除する。削除行の数量列には直前の正数が残るが、残高判定と一覧は論理削除状態を使う。編集・再購入時は元のIDを復元する。
- **開始残高の保持**：有効な連動履歴が参照する保有は、SQLiteの `keep_ledger_holding` トリガーで物理削除を防ぐ。既存の90日整理処理を変更せずに履歴編集のための開始残高を維持する。全履歴が論理削除されれば保有の物理削除は可能。
- **同日記録**：日付、作成日時、IDの順に再計算する。新規取引の作成日時は既存の最大値より後にし、同一ミリ秒の登録でも順序を安定させる。
- **取引の識別情報**：編集では口座・銘柄・市場を変更不可にした。移動が必要な場合は削除と再登録を行う。日付・種別・数量・単価・手数料・レート・メモは編集できる。
- **保有の重複**：同じ口座・銘柄・市場で有効な保有が複数ある場合、任意の1行に反映せず400を返す。
- **円換算**：日本株とJPYクォートFXは倍率1、米国株とUSDクォートFXは各記録の `fx_rate` を使用。現在値を過去の不明レートの代用にはしない。フォームの現在値は保存済み価格がある場合のみ使用する。取引一覧は通貨記号付きの現地通貨表示、集計帯は円表示。
- **件数**：年別の取引件数は配当を含む全記録を数える。種別フィルタは一覧・CSVに反映し、集計帯は選択年の全記録を対象とする。
- **CASH**：履歴は保存できるが、保有数量の自動更新・実現損益計算は行わない。

## 未対応・相談事項

1. 上記の既存同期テスト1件の修正は変更許可範囲外。全体テストを成功させるには対応が必要。
2. `src/lib/db/backup.ts` は変更許可範囲外。現行JSONインポートは新しい取引列・開始残高列を復元しないため、別DBへのJSON復元では連動情報を引き継げない。同じDBへの復元でも既存行の新列が残り、JSONの内容との整合に注意が必要。SQLiteファイルのコピーは全列を保持する。同一スキーマ間のLAN同期は既存の全列交換対象にこれらの列も含まれるが、同時編集時の行単位競合の性質は従来どおり。
3. 記録連動後も保有編集画面で数量・取得単価を手入力できるが、取引を次に変更すると保存済み開始残高と履歴から再計算される。手入力調整を継続的に反映するための調整記録は未実装。
4. ブラウザーの利用不可により、実画面の外観・レスポンシブ表示・マウス操作は未検証。
5. 検証用の `tmp/t18/` に、コピー元・実行用SQLiteとそのWAL/SHMファイルが残っている。自動承認レビューが削除コマンドを `blocked by policy` で拒否したため削除できなかった。すべて新規作成した検証用データで、実DBのコピーではない。
