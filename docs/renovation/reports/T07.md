## プロトコルの最終仕様

### 共通

- すべてJSON。成功・失敗とも `Cache-Control: no-store`。同期ルートは `runtime = 'nodejs'`、`dynamic = 'force-dynamic'`。
- エラーは `{ "error": "説明" }`。入力不正400、認証失敗401、対象なし404、ID重複・同期実行中409、相手情報の不整合502、その他の実行失敗500。
- 自分の画面用APIは指示どおり中継対象外。Next.jsの待受設定は変更していない。
- 日時はUTCのISO形式。新規発行値はミリ秒付き。旧DBの互換性のため秒単位の `2024-01-01T00:00:00Z` も許容し、受信値をそのまま保存する。
- `PM_SYNC_PORT` は案内アドレスのポート、`PM_SYNC_PUBLIC_PORT` はLink要求で相手へ伝える自分のポート。どちらも既定38400。
- アドレスは `192.168.1.20:38400`、`http://127.0.0.1:3102` など。HTTP/HTTPSのoriginだけを許容し、認証情報やパス付きURL、リダイレクトは拒否する。
- 疎通確認は2秒、ペアリング・差分取得・反映は30秒でタイムアウトする。

### ペアリングと画面向けAPI

```json
POST /api/sync/pairing の応答例
{
  "code": "012345",
  "expiresAt": "2026-10-22T01:05:00.000Z",
  "deviceId": "<自分のUUID>",
  "deviceName": "作業PC",
  "addresses": ["192.168.1.10:38400"]
}
```

コードは5分有効・1回限り。再発行で前のコードを置換し、使用・停止・ID再生成で破棄する。受付状態はプロセス内で保持し、再起動後は再発行が必要。

```json
POST /api/sync/peers の入力例
{ "address": "http://127.0.0.1:3102", "code": "012345" }

このAPIが相手の POST /api/sync/peer/pair へ送る内容
{
  "code": "012345",
  "deviceId": "<自分のUUID>",
  "deviceName": "作業PC",
  "port": 3101
}

peer/pair の応答例
{ "deviceId": "<相手のUUID>", "deviceName": "別PC", "secret": "<64文字のhex>" }
```

シークレットは暗号学的乱数32バイトをhexにしたもの。受け側は `X-Forwarded-For` の先頭IPを使い、ヘッダーなしなら `127.0.0.1` と、要求の `port` から相手の `base_url` を保存する。

- `POST /api/sync/peers` は201で `{ "peer": <secretを除くsync_peers行> }`。
- `GET /api/sync/peers` は `{ "peers": [<secretを除く行 + reachable + 成功時serverTime>] }`。
- `DELETE /api/sync/pairing` と `DELETE /api/sync/peers/<id>` は `{ "success": true }`。
- `POST /api/sync/device/regenerate` は `{ "deviceId": "<新UUID>", "deviceName": "作業PC" }`。相手登録を全削除し、`sync_meta` の `last_*` も削除する。業務行の過去の更新元とログは保持する。
- `GET /api/sync/log` は `{ "logs": [<sync_logの直近50行>] }`。同時刻のログは挿入順の降順。

### HMAC

`peer/pair` 以外の `peer/*` には次のヘッダーが必須。

```text
X-PM-Device: <送信側UUID>
X-PM-Timestamp: 2026-10-22T01:00:00.000Z
X-PM-Signature: <HMAC-SHA256の64文字hex>
```

鍵はhexを復号した32バイト。署名対象は次のUTF-8文字列で、区切りはLF。

```text
METHOD\n/path?query\nTIMESTAMP\nSHA256_HEX(BODY)
```

メソッドは大文字、パスには送信時のクエリ文字列を含む。本文は送信した文字列そのままで、GETは空文字列。未登録デバイス、受信時刻から前後5分超、時刻形式不正、署名不一致は401。署名比較に `crypto.timingSafeEqual` を使う。

`GET /api/sync/peer/ping` は `{ "deviceId", "deviceName", "serverTime" }` を返す。

### 差分と反映

`GET /api/sync/peer/changes?since=<URLエンコードした日時>` の応答は `{ "changes": <下記の差分>, "serverTime": "..." }`。`since` 省略で全件。`serverTime` は収集前に採り、境界後の変更を次回に残す。通常の差分では呼出し元デバイスによる更新を送り返さない。

```json
POST /api/sync/peer/apply の入力例
{
  "changes": {
    "portfolios": [],
    "holdings": [],
    "transactions": [],
    "trade_ideas": [{
      "id": "<行UUID>",
      "symbol": "AAPL",
      "market": "US",
      "note": "確認メモ",
      "created_at": "2026-10-22T01:00:00.000Z",
      "updated_at": "2026-10-22T01:00:00.000Z",
      "deleted_at": null,
      "updated_by": "<更新元UUID>"
    }],
    "ticker_presets": [],
    "watchlist_items": []
  },
  "lastSyncedAt": null
}
```

差分は6つのテーブルキーを必須とし、行はDBの全列を含む。NULL列も省略しない。対象外のテーブル・列、不正な日時・値型・重複IDは拒否する。受信した `updated_at` と `updated_by` を自動時刻付けせず保存する。

反映結果は次の形。

```json
{
  "applied": 1,
  "skipped": 0,
  "conflicts": 0,
  "conflictDetails": [],
  "canonicalChanges": {
    "portfolios": [], "holdings": [], "transactions": [],
    "trade_ideas": [], "ticker_presets": [], "watchlist_items": []
  }
}
```

競合詳細は `{ "table", "id", "winner": "localまたはremote", "localUpdatedAt", "remoteUpdatedAt" }`。`local/remote` はその反映処理の受信側から見た区分。内容比較からID・更新日時・更新元を除き、論理削除を含む内容が違うかを調べる。初回の `lastSyncedAt: null` では既存行の変更を比較対象にする。

`canonicalChanges` はID統合で決まった正規行。内容の更新元が相手でもID統合を伝えられるよう、受信時の統合結果は通常の更新元除外と別に送信し、相手側で見つかった統合結果はapply応答から取り込む。`collectChanges()` 自体の更新元除外規則は維持している。

### 同期実行

`POST /api/sync/run` の入力は `{ "peerId": "<sync_peers.id>" }`。

```json
{
  "received": 1,
  "sent": 0,
  "conflicts": 0,
  "conflictDetails": [],
  "clockSkewMs": 4,
  "warnings": [],
  "durationMs": 51
}
```

- `received/sent` は転送行数ではなく実際の反映件数。受信側のID統合反映も件数に含む。完全に同じ行や古い行を再送しても反映件数は増えない。
- `clockSkewMs` は往復の中間時刻に対する相手時計の差。正は相手が進んでいることを表す。絶対値3分超なら `warnings` に日本語警告を含む。
- 5分重ねて取得・送信し、受信位置は相手の収集開始時刻、送信位置は自分の収集開始時刻に進める。受信確定後に送信が失敗した場合は受信位置だけを保存する。
- 競合件数は指示の条件どおり「自分の行が最終同期後に更新され、受信内容と異なる」場合。5分の重なりで再取得した古い内容との相違も該当するため、手動確認の編集・削除でも1件になった。同じ行と同じ日時の組合せを送受信の両方で検出しても集計は1件にする。
- 排他はDBパス単位で、このNext.jsプロセスの全ルート間で共有する。同期中のLink登録・解除とID再生成も409にする。
- バックアップ先は接続DBの親フォルダの `sync-backups/portfolio-<UTC日時>-<UUID>.db`。`db.backup()` を使い、直近10件を保持する。
- 成功・失敗とも `sync_log` に反映件数・競合・終了日時・詳細を保存する。成功後に90日超の論理削除行を掃除する。

## 判断事項

- `openDatabase(path)` は空の検証DBも作れるようにマイグレーションだけを行い、モックデータは投入しない。既存 `getDb()` のシードと共有接続の挙動は維持した。
- 既存の `src/lib/db/maintenance.ts` は `getDb()` 固定だった。変更許可の対象外のため編集せず、同期側にDB引数を取る同じ保持規則の `purgeDeletedRows(db)` を実装した。子行を先に消し、参照が残る口座は保持する。
- 同一銘柄のID統合結果は内容の更新ではないため、日時・更新元を付け直して送り返す方式を採らず、`canonicalChanges` で明示的に伝える方式にした。
- 旧DBの秒単位日時を変更せず扱うため、差分のsince比較にはSQLiteの `julianday`、LWWと競合の比較には時刻値を使う。日時表記の桁数で勝敗が変わることを防いだ。
- シークレット・同期状態を含むDBバックアップは、指示どおり同期前のDB全体を保持する。通常の既存バックアップAPIの形式は変更していない。
