# T30 Windowsデスクトップ統合 実施レポート

実施日: 2026-10-23〜24（JST）

## 実施内容

タスクバーのAppUserModelID・アイコン・再起動コマンドを統一し、非表示起動用VBS、ショートカット作成、単一起動、終了処理を実装した。アプリの実起動・本番ビルド・実際のショートカット作成は指示どおり行っていない。実DBを開いていない。

## 原因

以下は既存コードから確認した不備であり、実アプリを起動して現象を再現した結果ではない。

- 旧runnerは `shell: true` で `npm.cmd run start` を起動し、保持するPIDがcmd/npmのラッパーだった。Electronも `run-electron.mjs` を介した起動だったため、直接の子プロセスと実際のアプリ／サーバーの間に中間プロセスがあった。
- `terminateProcessTree()` は `taskkill /t /f` をspawnするだけで完了・失敗を待たず、runnerは100ms後に `process.exit()` していた。終了要求が成功したか確認できず、親終了後の後始末も保証されなかった。
- `child.killed` は終了シグナルの送信状態で、終了完了を意味しないが、旧処理はこのフラグでも回収を省略していた。また、追跡する親PIDがすでに終了すると、その子孫の回収も省略されていた。
- Windowsでコンソールを閉じる／プロセスを強制終了する場合、JavaScriptのSIGINT/SIGTERMハンドラーや非同期処理だけでは後始末を保証できない。旧実装にはOS側で子孫をまとめて回収する仕組みがなかった。
- 配布版の `before-quit` もリレーの非同期closeを待たず、サーバーに `kill()` するだけだった。
- mDNSのcloseはgoodbye送信のコールバックだけでソケットを閉じており、完了通知や送信停滞時の期限がなかった。更新中のmDNS初期化と終了の競合にも対処が必要だった。
- `BrowserWindow` のアイコンだけでは、タスクバー固定の再起動先やAppUserModelID付きリンクは設定されていなかった。加えて、インストール済みElectronの `default_app.asar` を読み取ったところ、`.mjs` ファイルを直接渡す起動ではルートの `package.json` が読み込まれず、アプリパスも `electron` ディレクトリになることを確認した。従来の `app.getAppPath()/build/icon.ico` はリポジトリのアイコンを参照できない構造だった。

## 判断したこと

- **終了保証**: 追加依存を使わず、非表示PowerShellからWin32 APIを呼び、`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を設定する。監視プロセスはrunnerをJobへ登録し、準備完了後にだけElectron／Next.jsを起動する。監視側は親のネイティブプロセスハンドルを待ち、親終了時または監視自体の終了時にJob内の子孫を回収する。通常終了ではtaskkillとサービスcloseも待ち、全体に12秒の期限を設けた。監視初期化に失敗した場合は子プロセス起動前に中止する。
- **二重起動**: Electronの単一起動ロックを先に取得する。IPCの準備応答を受けたrunnerだけがビルド／Next.js／同期サービスを起動する。2つ目のElectronは `second-instance` を通知して終了する。
- **アプリ識別**: Electronには `main.mjs` ファイルではなくリポジトリルートを渡し、`package.json` の `productName` と `main` を使う。アイコンはモジュール位置から求めたルートで解決する。開発版のElectronユーザーデータ（ブラウザーキャッシュ等）は既定名ElectronからPortfolio Manager名になる可能性があるが、SQLiteのパスは変更していない。
- **旧孤立サーバー**: 使用中ポートを警告して別ポートを選ぶ許容方式を採用した。所有者を断定して旧プロセスを自動終了する処理は設けていない。以前の孤立Next.jsも残したまま回避できる。他アプリ／別の作業環境を誤終了させないための判断で、手動調査手順をDESKTOP.mdへ記載した。
- **リンク**: リポジトリ版は `wscript.exe //B //Nologo "...launch-desktop.vbs"` をリンク先・タスクバーの再起動先に共通使用する。配布版の自己起動リンクは配布実行ファイルを参照する。起動時はスタートメニューのみ更新し、デスクトップは明示コマンドの実行時だけ作成する。
- **ログ**: VBS起動時に `data/logs/desktop-YYYYMMDD.log` へ追記する。日付は起動日のローカル日付で、稼働途中のローテーションは行わない。従来のビルド未作成時の自動ビルド動作は維持し、そのプロセスも追跡・回収する。

## レビュー担当の実機確認手順

この節は未実行。実機確認者の環境で実施する。

1. 必要に応じて作業用DBをコピーし、`SQLITE_DB_PATH` をそのコピーの絶対パスへ設定する。実DBを使わずに確認する場合は `PM_FORBID_REAL_DB=1` も維持する。
2. リポジトリで `npm run desktop:shortcuts` を実行する。スタートメニューとデスクトップの両リンクがVBSを参照し、AppUserModelID・`build/icon.ico`・作業ディレクトリが正しいことを確認する。同じコマンドを再実行し、同一内容のリンクの更新日時が変わらないことを確認する。
3. デスクトップのリンクから起動する。黒いコマンドウィンドウ／別のcmdタスクバーボタンが出ず、新アイコンのアプリが1つだけ表示されること、日別ログが作成されることを確認する。初回ビルドが必要な場合は完了を待つ。
4. アプリを最小化して同じリンクを再度開く。既存ウィンドウが復元・前面表示され、Next.js・リレーの追加起動や同期ポート競合がないことを確認する。起動途中にも2回開いて確認する。
5. 古いタスクバー固定を外し、新しいアプリを固定する。終了後、固定ボタンから再起動し、アイコン・グループ化・非表示起動が維持されることを確認する。アイコンキャッシュの対処はDESKTOP.md参照。
6. ログのURLで今回選択されたWebポートと、起動したrunner／Next.js／ElectronのPIDを記録する。ウィンドウの×で閉じ、数秒後にそれらのプロセス、Web待受、同期TCPポートが残らないことを確認する。mDNSはUDP5353を他アプリも使うため、記録したrunnerのPIDに紐づくエンドポイントが消えたことを確認する。
7. 再起動し、今回起動したElectronのメインPIDだけをタスクマネージャー等で強制終了する。同様にNext.js・runner・同期サービスが残らないことを確認する。renderer異常終了でもアプリ全体が終了することを確認する。
8. `npm run desktop:start` をコンソールから起動し、ウィンドウの×・Ctrl+C・コンソールウィンドウの×をそれぞれ別の起動で試す。さらに今回のrunner PIDだけを強制終了するケースも試し、毎回記録した子孫と待受が消えることを確認する。
9. 3001を検証用の無関係な待受プロセスで占有して起動する。既存の待受を終了せず、ログに警告と3002以降の選択URLが残ることを確認する。旧版の孤立Next.jsを確認する場合も同じ期待結果となる。
10. 配布版にも反映する場合は、新たにimportされる `electron/desktop-runner.mjs`・`electron/discovery.mjs`・`scripts/create-shortcuts.mjs` を含めて配布資材を更新し、配布実行ファイルのリンク先・内蔵サーバー終了・ログも確認する。

- 外部の `D:\code\pm-ai-logs\start-portfolio.cmd` は変更許可範囲外のため変更していない。新ショートカットまたはリポジトリ内VBSを起動入口として利用する。
